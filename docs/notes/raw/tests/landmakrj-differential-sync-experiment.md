# Land Maker (landmakrj) Netplay Differential Sync Experiment

Empirical investigation into the minimal synchronization payload at the 2P versus trigger for deterministic netplay.

## Experimental Setup

Two independent machine instances were cold-booted and reached the 2P versus trigger frame via different paths:
- **Path A (Machine A)**: Attract mode 700 frames; coins inserted at frames 700 and 720; start at frame 800; right arrow at frame 1400; B1 confirm at frame 2000. Reached trigger at frame 2065. Initial RNG `0x400826 = 0xc63c46c0`.
- **Path B (Machine B)**: Attract mode 1500 frames (500 frames longer attract duration); coins at frames 1500 and 1520; start at frame 1600; right arrow at frame 2200; B1 confirm at frame 2700. Reached trigger at frame 2945. Initial RNG `0x400826 = 0x08a03240`.

At the trigger frame (`0x401f6e` 0 -> 1), full machine state snapshots (`resA.saved_state` and `resB.saved_state`) were saved.

Both machines were then stepped in lockstep for up to 8,000 frames using identical match input schedules (`1-30000 mash keys=b1 period=45 seed=5`) under varying synchronization specifications.

## Experiment Series

### Spec 0: No Sync (Baseline Control)
- **Sync Payload**: 0 bytes copied.
- **Observed**:
  - Work RAM diverged immediately at step 1 (2,639 bytes differed on step 1; 5,462 distinct addresses across 2,000 frames).
  - Graphics RAM and Palette RAM diverged at step 1.

  - Match outcome diverged completely.

- **Sync Payload**: `0x400826..0x400829` (4 bytes copied from A to B at trigger).
- **Observed**:
  - Work RAM diverged at step 1 (2,635 bytes differed due to unsynchronized timer/frame counters and leftover attract buffers).
  - At step 2000, 3,340 bytes differed.

### Spec 3: Minimal Gameplay Set (550 bytes) without per-frame reseed
- **Sync Payload**:
  - `0x400826..0x400829` (4 bytes): LCG RNG seed

  - `0x4078f0..0x40791f` (48 bytes): Character selection menu state, cursor indices
  - `0x40fc58..0x40fc59` (2 bytes): Match rounds setting
  - Total: 550 bytes.
- **Observed**:
  - For steps 1..1379 (entire Character Select sequence): Gameplay block `0x401f40..0x40212f` and piece generator seeds (`0x40203c`, `0x4020e4`) remained **100% byte-identical** (e.g. at step 500 and 1000, `p1_rng = 0x31981280` on both peers).
  - At step 1380: Exactly 1 byte diverged: `0x401f55` (low byte of `0x401f54`, stage theme): Machine A drew theme 1, Machine B drew theme 4.

- **Leak Diagnosis**:
  The 68EC020 idle loop at ROM `$19f8` spins on every spare cycle waiting for VBlank, calling ROM `$1468` which advances `0x400826`. Sub-frame cycle deadline differences accumulated over 1,380 frames of character select, causing `0x400826` to drift before the stage pick at step 1380.

### Spec 4: Gameplay RAM + Attempted CPU Cycle Sync

## Non-Gameplay State Divergence & Netplay Desync Hashing

Because Machine A and Machine B ran different numbers of frames prior to the 2P trigger (2,065 vs 2,945 frames):
- Sound CPU (68000), ES5510 DSP sample registers, and DUART timer clocks have different cycle origins.
- Palette RAM (`0x600000..0x607fff`) and Graphics RAM (`0x620000..0x65ffff`) retain unused sprite tables and line-RAM latch states from prior attract loops.
- Work RAM master frame counter (`0x400142`) and timer ticks (`0x40032c`) differ.
- Consequently, whole-machine `Machine::state_crc()` differs every frame.

**Desync Hash Recommendation**:
Netplay desync detection must hash the gameplay-critical state, not `Machine::state_crc()`.
Recommended hash region:
- **Span**: `0x401f40 .. 0x402130` (496 bytes).
- Contains mode state, round win counters, match over flags, P1/P2 board blocks, piece generators, and selected characters.
- Evaluated every $N$ frames (e.g. every 60 frames) during active gameplay.

## Gameplay Feel Analysis

The per-frame RNG reseed rule `0x400826 = f(shared_seed, match_frame)` introduces no observable changes to gameplay feel:
1. **Piece Sequence**: Piece generation in `sub_093a1c` consumes random numbers from player-specific seeds at `0x40203c` and `0x4020e4` using the authentic ROM `$1468` LCG math ($X_{n+1} = 7X_n + 5$). Piece delivery strictly follows original arcade mechanics.
2. **Stage Variety**: `round_task` consumes `0x400826` once per round at `0x08e470` to select a stage theme. `splitmix32` provides a uniform, uncorrelated 64-bit mixer with full avalanche, ensuring stage variety is authentically random while remaining identical on both peers.

None of these five bytes affect board state, piece delivery, collision, win conditions, or simulation outcome.

### Dynamic Hash Strategy

To avoid false positive desyncs during character select while ensuring complete board-level verification during active play:
- **Synchronized Range Set (80 Bytes)**:
  - `0x401f40..0x401f83` (68 B): Mode block
  - `0x40203c..0x40203f` (4 B): Player 1 piece generator RNG seed
  - `0x4020e4..0x4020e7` (4 B): Player 2 piece generator RNG seed
  - `0x40210e..0x40210f` (2 B): In-game play task latch (`-$5ef2(a5)`, 0 pre-init, 1 initialized)
  - `0x40fc58..0x40fc59` (2 B): Match rounds setting word
- **Initialization Signal**: `m.read16(0x401f82) >= 0x0050 && m.read16(0x40210e) == 1`
  - `0x401f82` is the mode block phase word within the 68 B synchronized mode block (`0x401f40..0x401f83`, offset 66–67).
  - Holds `0x004e` during character select and versus intro (match frames 1..1509).
  - Transitions to `>= 0x0050` (`0x0055`) at match frame 1510 upon round 1 scene switch.
  - `0x40210e` (`-$5ef2(a5)`) is the gameplay task latch, written with 1 as the very first instruction of `sub_093462` at match frame 1516 (`0x93462 move.w -$6092(a5), -$5ef2(a5)`). It remains 1 across all rounds and inter-round transitions.
  - Gate evaluates to FALSE throughout the 6-frame transition window (frames 1510..1515) and flips to TRUE at exact match frame 1516.
  - Because all gate fields are strictly within `sync_ranges`, both peers agree unconditionally.
- **Phase 1 (Frames 1..1515)**: CRC32 over the 80 B synchronized ranges (`sync_ranges`).
- **Phase 2 (Frames 1516..5000)**: Full-block CRC32 over `0x401f40..0x40212f` (496 B) excluding the five cosmetic/residue bytes `0x401f85`, `0x401fa1`, `0x402033`, `0x4020db`, `0x4020f7`.
- **Verification**: An empirical test computing CRC reports on EVERY SINGLE FRAME from 1 to 5000 (`--crc-every 1`) passed with 100% parity across all 5,000 frames and zero desyncs. Full-block hash is active for all 3,485 frames of actual round play.

## Credit Storage, Simulation Relevance, and Sync Fix (Spec 7, 96 Bytes)

### Where Credits Live
- `0x400090` (`-$7f70(a5)`, 2 bytes, uint16_t): Main credit counter (0..9).
- `0x400092` (`-$7f6e(a5)`, 2 bytes, uint16_t): Chute 1 partial coin accumulator.
- `0x400096` (`-$7f6a(a5)`, 4 bytes): Chute 1 coin switch debounce state.
- `0x40009a` (`-$7f66(a5)`, 4 bytes): Chute 2 coin switch debounce state.
- `0x40009e` (`-$7f62(a5)`, 2 bytes, uint16_t): Chute 2 partial coin accumulator.
- `0x4000ac` (`-$7f54(a5)`, 2 bytes): Total lifetime coin meter audit.

### Why Credits Matter to the Simulation
1. **Challenger joins**: Gameplay loop calls `sub_08f398` every frame (`0x08e4f4`), which tests `0x400090` (`0x08f3ee: tst.w -$7f70(a5)`). If credits > 0, pressing start triggers `sub_08f0d6` and the challenger banner; if credits == 0, the start press is rejected. Differing credits cause divergent player-join behavior.
2. **Continue countdown**: Match end countdown (`sub_08ee46`) checks credits via `sub_000ad6`. If credits >= 1, pressing start continues the match and deducts 1 credit (`sub_000b1e`); if credits == 0, start is rejected and the game returns to attract.
3. **Credit text formatting**: On every frame, `sub_08df3c` reads `0x400090` (`0x08df78: move.w -$7f70(a5), d0`) and formats the number into text RAM at `0x61ce4a` ("CREDIT N").

### Chosen Solution: Overwrite Client with Host Credits via Sync Blob (Option C)
Rather than zeroing credits (which discards the host player's real coins), the host's credit state is included in the sync blob and copied to the client on connect:
- **Extended Sync Range**: Add `0x400090 .. 0x40009f` (16 bytes) to `sync_ranges`.
  - Captures: credits counter (`0x400090`), partial coins (`0x400092`, `0x40009e`), and coin debounce states (`0x400096`, `0x40009a`).
  - Total sync payload size: 80 bytes + 16 bytes = **96 bytes**.
- **Result**:
  - Client credits immediately match Host credits on connect.
  - Both screens display identical "CREDIT N" text at `0x61ce4a`.
  - Both peers have identical continue / challenger permissions.

### Verification Run (Spec 7, 96 Bytes)
Tested with differing pre-trigger histories:
- Host inserted 6 coins total (4 credits remaining after 2P start, trigger frame 1465).
- Client inserted 2 coins total (0 credits remaining after 2P start, trigger frame 2165; 700 frames dwell difference).
- Client applied the 96 B sync blob on connect: Client credits immediately became 6.
- Advanced for 5,000 match frames with human-like character select inputs and per-frame RNG reseed:
  - `frame 1000`: `gate=1, crc=0x58328372` on both peers (stage 2/2, credits 6/6).
  - `frame 2000`: `gate=1, crc=0xe8dd7638` on both peers.
  - `frame 3000`: `gate=1, crc=0x3bd78f8c` on both peers (P2 won round 1, stage 5/5).
  - `frame 5000`: `gate=1, crc=0xd842315b` on both peers.
  - **Result**: **100% byte-exact parity across all 5,000 frames with zero desyncs**.

## Root Cause of Frame 900 Desync: How Credits Leaked into the 496 B Hashed Block

Although the primary credit counter `0x400090` (`-$7f70(a5)`) lives outside `0x401f40..0x40212f`, differing credit counts directly cause bytes **inside** the 496 B block to differ when the hash gate flips:

### 1. The Gate Flip Mechanism
In `games/landmakrj/netplay/netplay.cpp`:
```cpp
const bool gameplay_active = (m.read16(0x401f82) >= 0x0050 && m.read16(0x40210e) == 1);
```
- `0x401f82` (`-$607e(a5)`, word) stores the current sound/BGM command ID (`0x4e` during character select, `0x55`/`0x5d` during match/round play).
- `0x40210e` (`-$5ef2(a5)`, word) is the match play latch initialized to 1 by `sub_093462` at round start.
- When human players confirmed character selection quickly (around frames 480..661 in session `6bcc777d9b933089`), character select finished and round 1 ("READY" screen) began at match frame 900.
- At match frame 900, `0x401f82` transitioned to `0x55` and `0x40210e` was 1, flipping `gameplay_active` to `true`.
- The hash immediately switched from Phase 1 (80 B synced ranges) to Phase 2 (the full 496 B block `0x401f40..0x40212f`, excluding 5 bytes).

### 2. Credit-Derived Bytes Inside the 496 B Block
During Character Select, routine `sub_08f398` executes every frame and invokes `sub_08f486` (the credit check, blink timer, and on-screen prompt handler):
- **`0x401f58` (`-$60a8(a5)`, word, 2 bytes)**: Free-running 60-frame credit prompt blink timer. Decremented on every frame by `sub_08f486` at PC `0x08f486`; reloaded with `#$3c` (60) when reaching zero.
- **`0x401f5a` (`-$60a6(a5)`, word, 2 bytes)**: Credit prompt blink phase toggle. Bit 0 is inverted by `sub_08f486` at PC `0x08f492` (`bchg.b #0, -$60a6(a5)`) whenever the timer expires.
- **`0x401f44` (`-$60bc(a5)`, word, 2 bytes)**: Credit display suppression / game in progress flag. Routine `sub_08f486` tests `0x400090` at PC `0x08f4aa` (`jsr $ad6.l`). If credits >= 1, it writes `move.w #1, -$60bc(a5)` at PC `0x08f4d2`; if credits == 0, it branches to `0x08f4f0` ("INSERT COIN(S)" logic) and does not set this flag.

**None of `0x401f44`, `0x401f58`, or `0x401f5a` were in the 5 excluded bytes** (`0x401f85, 0x401fa1, 0x402033, 0x4020db, 0x4020f7`). Consequently, differing credit counts (CREDIT 4 on Host vs CREDIT 1/0 on Client) caused `0x401f44`, `0x401f58`, and `0x401f5a` inside the 496 B block to carry differing values at match frame 900, producing the immediate CRC mismatch (`crc_p1 = 0x81c4dc49`, `crc_p2 = 0xa1dad6cd`) as soon as the gate flipped!

## Related Machine Settings Audit (EEPROM / NVRAM)

Other per-machine settings in the same architectural family as credits that influence RAM state:

1. **Free-Play Flag (`0x4000cd`, byte, `-$7f33(a5)`) & Setting (`0x4000d3`, byte, `-$7f2d(a5)`)**:
   - Loaded from EEPROM byte `$18(a2)` bit 7 by `sub_005006` at PC `0x005070`.
   - Read by `sub_000ad6` (credit check bypass), `sub_08df50` (draws "FREE PLAY" text), and `sub_08e236`.
   - **Desync Risk**: **HIGH**. If Peer A has Free Play enabled and Peer B has Coin Play, `sub_000ad6` bypasses credit checks on A but executes them on B; coin deduction is skipped on A but decrements on B; and text RAM renders "FREE PLAY" on A vs "CREDIT N" on B, causing instant desync.

2. **Game Difficulty & 2P Mode Enable (`0x4000ce`, byte, `-$7f32(a5)`)**:
   - Unpacked from EEPROM byte `$a(a2){11:3}` by `sub_005006` at PC `0x005044` (3 bits: difficulty level 0..7).
   - Bit 0 controls whether 2-player mode is allowed: read by `sub_08e2a0` (allows P2 start), `sub_08f2de` (allows P2 challenger join), and `sub_09ef9a` (controls whether Game Select menu offers "2P VS").
   - **Desync Risk**: **CRITICAL**. If two peers have differing bit 0 settings, the Game Select menu on one machine will not offer 2P VS at all, preventing the match from starting identically.

3. **Coinage Setting (`0x4000d0`, byte, `-$7f30(a5)`) & Rates (`0x4000cb`, `0x4000cc`)**:
   - Unpacked from EEPROM by `sub_005006` at PC `0x005060`. Controls coins-per-credit ratios for chutes 1 and 2.
   - **Desync Risk**: High if coins are inserted during play; mitigated by syncing the credit block.

4. **Screen Flip (`0x40013e`, word, `-$7ec2(a5)`)**:
   - Unpacked from EEPROM byte `$a(a2)` bit 7 by `sub_005006` at PC `0x005034`. Controls cocktail/flip orientation.
   - Visual only; does not affect piece logic.

5. **Match Rounds Setting (`0x40fc58`, word, `+$7c58(a5)`)**:
   - Unpacked from EEPROM byte `$18(a2){2:3}` by `sub_005006` at PC `0x0050d0`.
   - **Already synchronized** in the netplay sync ranges (2 bytes).

### Conclusion on EEPROM Settings
Two machines with different EEPROM configurations (particularly Free Play `0x4000cd` or Difficulty/2P bit 0 `0x4000ce`) **will desync**. For production netplay, peers should either share a canonical EEPROM configuration or synchronize the settings block (`0x4000cd..0x4000d3`, 7 bytes) at connect.

## Lobby Hold and Un-commit Architecture

When the frontend opens a netplay lobby upon 2P versus trigger detection, the game scene must hold visually while preventing game logic progression. If netplay is cancelled, the frontend must un-commit the selection and return cleanly to the Game Select menu with full timer and active cursor.

### 1. Task Scheduler & Scene Driving Tasks
Analysis of the cooperative task table (`0x400330..0x400380`, active mask at `0x400378`) during Game Select reveals:
- **Task 12 (`sub_09e962`, priority $c)**: The Game Select menu master task. Runs the menu loop at `0x09e9bc`, calling `sub_09ec9a` each frame.
- **Task 7 (`sub_003d5e`, priority $7)**: The sparkle actor engine. Iterates through 128 actor records in `0x40b420..0x412720`, animating the sparkles flying toward the center.
- **Task 10 (`sub_08e0cc`, priority $a)**: Tile/palette transition helper.
- **Task 14 (`sub_004498`, priority $e)**: Master sprite list generator (`sub_004528` command processor).
- **Task 15 (`sub_010170`, priority $f)**: Raster timing, palette fade (`sub_0102e8`), and hardware color RAM writer (`sub_000ce0`).
- **Task 1 (`sub_08e20c` / `sub_08edde`, priority $1)**: Main game supervisor task. Yields at `0x08edf0` awaiting Task 12 termination. When Task 12 terminates, Task 1 writes `0x401f6e = 1` at PC `0x08edfe` and proceeds to launch Character Select (`sub_08ee06` at `0x08e45a`).

### 2. Animation Mechanics
- **Background Galaxy Swirl**: Driven by `sub_09ecb0` (called every frame from Task 12). Reads sine table at ROM `0x001c84` and writes 256 scroll offsets into line RAM at `0x62a000`. The swirl angle counter is `0x40790a` (`-$6f6(a5)`, word), incremented by 2 on every frame (`0x09ecf0: addq.w #2, -$6f6(a5)`).
- **Menu Countdown Timer ('TIMER . N')**: Stored at `0x407908` (`-$6f8(a5)`, word, uint16_t). Initialized to `0x04b0` (1,200 frames = 10.0 seconds) at menu open (`0x09ec18`). Decremented by 1 every frame in `sub_09f170..0x09f172`. The on-screen digit is `timer / 120` (`0x09f17c: divu.w #$78, d0`).
- **Confirmation Animation**: When the player confirms option 2 '2P VS' via B1, `sub_09ef9a` writes `1` to `0x407902` (`-$6fe(a5)`) and plays sound `0x1c`. Routine `sub_09ecf6` increments flash counter `0x407903` (`-$6fd(a5)`) on each frame up to 64 (`#$40`). During these 64 frames, the '2P 対戦' tile glows gold with a gold border, the swirl rotates, and sparkles fly. At frame 64, `sub_09ecf6` writes `#$ff` to `0x407902`, breaking the loop and initiating scene exit.

## Exact Pin Rules & Hooks per Trigger Path

### Path 1: GAME SELECT Menu Path (frame ~1500 confirm, ~2065 exit)

1. **Pre-commit Trigger Predicate (`is_menu_confirm_moment`)**:
   Evaluated at each frame boundary:
   ```cpp
   bool is_menu_confirm_moment(Machine &m) {
       return m.read8(0x407902) == 1 && m.read16(0x401f66) == 0xffff;
   }
   ```
   Fires immediately when option 2 ('2P VS') is confirmed (by player B1 press or timer expiry). The frontend captures its local pre-commit snapshot at this frame.

2. **Lobby Hold Hook (`apply_menu_lobby_hold`)**:
   Applied after `m.run_frame()` on every frame while the lobby is open:
   - `0x407902` (byte): Pin to `1` (keeps confirmation state active).
   - `0x407903` (byte): Pin to `30` (freezes flash counter at 30, preventing it from reaching 64).
   - `0x407908` (word, uint16_t): Pin to `0x04b0` (freezes countdown timer at full value 1,200 frames / 10s).
   - `0x401f6e` (word, uint16_t): Pin to `0` (prevents premature versus latch trigger until lobby resolution).
   - **Observable Behavior**: Held across 600 frames (10 seconds) with zero crashes. Swirl rotates smoothly every frame, sparkles fly to center, BGM plays continuously, '2P 対戦' glows gold, timer displays 'TIMER 9' (frozen).

3. **Cancel Netplay Hook (`apply_menu_uncommit`)**:
   Invoked when the player cancels netplay without choosing Play locally:
   - `0x407902` = `0` (clear confirm flag)
   - `0x407903` = `0` (clear flash counter)
   - `0x407908` = `0x04b0` (reset countdown timer to full 1,200 frames / 10s)
   - `0x401f66` = `0` (clear VS mode selected flag)
   - `0x401f6e` = `0` (clear versus latch)
   - Clear player input words so no held button immediately re-confirms.
   - **Observable Behavior**: Game returns to interactive Game Select menu! Menu timer counts down naturally from 1,200 (`timer = 1140` at +60 frames), player can freely move cursor (verified moving left to '練習'), and select freely. No scene switch, no trigger refire.

4. **Play Locally**:
   Restore the pre-commit snapshot, unpin, and allow the 64-frame confirmation animation to conclude naturally into Character Select (`vs_latch = 1`, character select island appears).

### Path 2: Character Select Join Trigger (~1450)
- **Trigger**: Player 2 presses Start during 1P Character Select; `0x401f6e` transitions 0 -> 1 at PC `0x08ee2c`.
- **Lobby Hold Hook (`apply_charsel_lobby_hold`)**:
   - `0x407908` (word, uint16_t) = `0x04b0` (freezes 1,200-frame character select countdown timer).
   - `0x407902` (byte) = `0` (prevents Player 1 auto-confirm).
   - `0x407904` (byte) = `0` (prevents Player 2 auto-confirm).
   - **Observable Behavior**: Character Select screen holds for 600 frames; water and character portraits animate, BGM plays, timer displays 'TIMER 9' (frozen).
- **Cancel Netplay Hook (`apply_charsel_uncommit`)**:
   - `0x401f6e` = `0` (reverts versus latch to 1P mode).
   - `0x401f53` = `0x41` (reverts active players to Player 1 only).
   - `0x407908` = `0x04b0` (resets timer).

### Path 3: Mid-Gameplay Challenger Trigger (~2300)
- **Trigger**: Player 2 presses Start mid 1P gameplay; banner concludes and Character Select launches at frame ~2300 (`0x401f6e` transitions 0 -> 1 at PC `0x08f7ee`).
- **Lobby Hold Hook**:
   - `0x407908` (word) = `0x04b0` (freezes character select countdown timer).
   - `0x407902` = `0`, `0x407904` = `0` (prevents auto-confirm).
   - **Observable Behavior**: Character Select screen holds for 600 frames; character portraits animate, BGM plays.
